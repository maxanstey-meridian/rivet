# Changelog

## 0.50.0 — unreleased

### Part 1: polymorphism done properly

A polymorphic variant used to be a throwaway inline object built beside the derived type, so it lost every annotation on the way, and imported hierarchies came back as shapes their source never wrote. Variants are now the derived record itself with the tag in front, imported hierarchies keep the schemas they came with, and the settings that make the host read or write what the spec can't describe are refused.

#### Breaking

- CLI: `RIV1015` is an error. A `[JsonPolymorphic]` type with no `[JsonDerivedType]` used to be flattened with a warning, but System.Text.Json refuses to serialize such a type at all ("should specify at least one derived type"), on .NET 8, 9 and 10. Register a derived type or remove the attribute. It, and `RIV1016` below, fire for a generic base too.
- CLI: a `[JsonDerivedType]` whose type isn't a named class, struct or record (`typeof(int[])`) is refused with `RIV1014`. It used to be skipped, leaving it out of the `oneOf` (System.Text.Json throws on it) or, when it was the only one, flattening the base.
- CLI: `RIV1016` is an error, and covers both directions. `UnknownDerivedTypeHandling = FallBackToBaseType`/`FallBackToNearestAncestor` writes an unregistered type as a base the `oneOf` doesn't admit; `IgnoreUnrecognizedTypeDiscriminators = true` reads an unknown tag as the base, which the `oneOf` rejects. An explicit `FailSerialization` is the default and is fine. The constant is now `Diagnostics.PolymorphicUnknownHandling`.
- `Rivet.Attributes`: `.ToResult()`/`.ToActionResult()` refuse a bound contract whose input reaches a polymorphic type, with a `RivetContractViolationException` naming the route, the input, the type, the path to it and the fix. System.Text.Json reads the discriminator only as the first property, and a JSON body can't promise that. On .NET 9+ setting `AllowOutOfOrderMetadataProperties = true` on the host's JSON options lifts it; on .NET 8 nothing does. An input that isn't a JSON body is refused on every runtime, because model binding reads it with no discriminator at all: a form (`.FormEncoded()`, `.AcceptsFile()`, a `multipart/form-data` or `application/x-www-form-urlencoded` `.RequestContent`, which import writes for every multipart operation, or a `TInput` that is or holds an `IFormFile`), and anything the spec reads from the route and query (GET, DELETE, HEAD and OPTIONS inputs, `Define.File<TInput>`, a POST/PUT/PATCH that declares a `.Parameter<T>()`, and `.AcceptsBinary()`). The tool and the runtime decide where the input goes with one shared function, and count an input as carrying files by one rule (the public properties ASP.NET binds, along the whole base chain, where a derived member of any accessibility hides its base's), which a test holds to one table of shapes. So the tool no longer writes multipart for an input whose only `IFormFile` is non-public (ASP.NET binds it as JSON). `.RequestBody()` makes any method's input a JSON body. Responses are unaffected.
- Contract JSON (`--from`): an endpoint-inline tagged union's variant object is no longer extracted into a `…Dto`/`…Response` component; it is emitted as its `{Base}_{Tag}` component with its description, scalar metadata and authored tag schema (objects nested inside it are still extracted). A variant with five or more fields, or repeated across endpoints, loses its extracted name, and so can a same-shaped object elsewhere that was only extracted because it paired with the variant (it stays inline under five fields, and its `Dto` name can change at five or more); with a `discriminatorSchema` the variant used to crash the emit.
- Contract JSON (`--from`): an inline-object field's `surface` is gone; write `readOnly`/`writeOnly`, the names a type's properties already use. The strict reader rejects `surface`.
- Contract JSON (`--from`): a variant that carries a `description`, `scalarMetadata` or `discriminatorSchema` must be an inline object with the tag property, and its `discriminatorSchema` must be a JSON object its tag satisfies (an `enum` or `const` that admits it, a `type` that includes `string`). Anything else is refused with the new `RIV2017`; it used to fail at emit with no ID, or ship a tag schema that refused the tag.
- CLI: a `[RivetGeneratedType]` `DiscriminatorSchemaJson` that isn't a JSON object, that its tag doesn't satisfy, or that sits on a type no base registers is refused with the new `RIV1122`. It used to fail at emit with no ID, ship as written, or be ignored.
- Import: a discriminator on a base extended through `allOf` (Bitbucket's `object`) becomes a hierarchy of inheriting `[JsonPolymorphic]` records, each registering every concrete descendant, with the tag property stripped (System.Text.Json writes it). Members are non-sealed, a base that is its own variant is non-abstract, records with members use init-only properties, and a redeclared member is `new`. An unknown tag fails to read.
- Import: a `oneOf` + discriminator whose sibling `required` names anything beyond the discriminator falls back to a union wrapper with `RIV3005`; it used to be reversed as if the sibling weren't there.
- Import: an `allOf` hierarchy C# can't hold falls back with a `RIV3005` naming why, where it used to drop dispatch silently or produce C# that didn't compile: a member that redeclares a property its chain requires with any change beyond documentation (a documentation-only restatement is fine and inherits; an `x-` extension's value counts as schema), one that refuses additional properties the root accepts, a descendant that also composes a `oneOf`/`anyOf`, a root reached only through several-`$ref` `allOf`s, an intermediate whose own `mapping` disagrees with its descendants' tags, and a `discriminator` beside a component's own `allOf` or dispatching over a union nested in it (one of Cloudflare's). The whole hierarchy is checked before any member is registered, so a record built earlier never names a member of one that then falls back (that used to leave `Team.Labels` typed `Labels` with no `Labels` generated).

#### Fixes

- CLI: a hand-written variant's `{Base}_{Tag}` component carries everything its record says: the type's description, and on every field the description, constraints, default, example, format, `deprecated` and `readOnly`/`writeOnly`. A `[RivetHeader]` member of a derived type is left out of its variant, as it is from the record.
- CLI: an imported variant keeps its component id and the tag schema its source wrote (Jira's `{ "type": "string", "description": … }`) instead of a synthesized `enum: [tag]`, and its type-level description.
- CLI: a component preserved verbatim is never rebuilt, so an imported `allOf` hierarchy or `oneOf` base is emitted as its source wrote it, with no orphan `{Base}_{Tag}` components beside it.
- Import: a `oneOf` whose sibling `properties`/`required` only restate the discriminator is reversed (Jira's last `RIV3005`), and a `oneOf` variant written as an `allOf` of a `$ref` and an object is flattened (six of Cloudflare's).
- Import: a `$ref` to a property-less hierarchy root resolves to its record instead of a `Dictionary`.
- Import: an `allOf` hierarchy member that restates an inherited required property without listing it keeps it required (no more CS9031), one that only adds an inherited optional property to its own `required` gets `new required`, and `[JsonExtensionData]` sits on the root only when every member admits extras. A restatement that changes only documentation inherits at any depth, inline enums and objects included, with no twin type or stray `new`. A property an ancestor lists in `required` but only a descendant declares is required on that descendant, and the tag property no longer leaves an unused inline enum (`AccountType`) behind.
- Import: a tag schema is admitted by the same rule generation checks it with, so import never writes a `DiscriminatorSchemaJson` that stops generation with `RIV1122`. A `oneOf` variant whose tag property constrains nothing (no `enum`, `const` or `type`) now reverses instead of dropping with `RIV3005`; a self-contradictory one (an `enum` beside a non-string `type`) drops loudly. In an `allOf` hierarchy a member's tag, whether the `mapping` names it or it's the component name, is admitted the same way by every declaration down its chain, so a declaration that constrains nothing (or none at all) no longer makes a member and its descendants abstract.
- Import: a `$ref` to any `allOf` hierarchy member resolves to its record, with `?` when the member admits null, whatever order the hierarchies are built in: a property-less nullable root is `Resource?`, and a typeless empty leaf the `mapping` names is `Leaf` rather than its root.
- CLI and import: a nullable polymorphic type (an imported hierarchy member or `oneOf` base written `nullable`) keeps its root schema metadata, so its use sites are a bare `$ref` instead of a `oneOf` with a null branch that rejected `null`.
- CLI: inline string and int enums that differ only in annotations no longer share a canonical name, so two `--from` unions that differ only there don't collide with a false `RIV2001`.
- `Rivet.Attributes`: a polymorphic input reached through a nullable struct member is found at its real path, and contract-violation messages name types readably (`List<Shape>`, not an assembly-qualified name).

#### New

- Contract JSON: inline-object fields take every property annotation, and tagged-union variants take `description`, `scalarMetadata` and `discriminatorSchema`.
- `Rivet.Attributes`: `RivetGeneratedTypeAttribute.DiscriminatorSchemaJson`.
- Corpus gate: Bitbucket is verified (22 of 25), with its 14 `RIV3024` source defects pinned.

### Part 3: generation tells the truth about the C#

Generation used to take the C# at its word in places where the C# was saying two things at once. A route constraint narrowed what routing admits and the spec never heard about it; a `[RivetSchemaType]` on a record vanished; a form's parts were named after a JSON body nobody sends; two examples pinned one component and the second quietly borrowed the first's value. Each of those now reaches the spec, or stops generation with an ID that says which half of the C# to change.

#### Breaking

- CLI: a route token with no typed declaration stops generation with `RIV1019`, now an error. A typed declaration is a matching input property, a type constraint (`{id:guid}`, `{page:int}`), a `.Parameter<T>(name, "path", ...)`, or, on a `[RivetEndpoint]` action, an action parameter. The token used to warn and go out as an untyped string, looser than whatever the handler binds; on a POST, PUT, or PATCH with no input type it didn't even warn. A token a `[RivetEndpoint]` action binds with no parameter used to be left out of the parameters while staying in the path, which is invalid OpenAPI; it's now typed by its constraint, or refused (G.4).
- CLI: a controller action named `…Async` behind an `[action]` token gets a new path, without the suffix, as MVC serves it: `[action]` on `FetchAsync` is `Fetch`, and an `[ActionName]` still wins. 0.49.0 kept the suffix, so the spec named a path the app never served. A controller class whose suffix is lowercase (`Widgetcontroller`) loses it too, in its `[controller]` token and its TS client group name.
- CLI: a route constraint types its path parameter and must agree with what declares it. `{id:int}` over a `string Id` (or a `.Parameter<string>("id", "path", ...)`, or a `[RivetEndpoint]` action's `string id`) stops generation with `RIV1125`. So do a keyword the type can't carry (`min(1)` on a string, `length(3)` on an int), two type constraints, two patterns, bounds that admit no value (exclusive ones included), and a `regex` with no pattern. A `number` the emitter writes as `integer` (`[RivetSchemaType("integer")] int`) agrees with `{id:int}`. Templates are read by ASP.NET routing's own parser, so one routing refuses at startup (`{a}{b}`, `{id?=5}`, an unclosed `{`) is `RIV1125` too. So is a route on a controller action, a `[RivetEndpoint]` method, or an abstract contract's method that repeats a parameter name; a static contract's field, the shape import writes, still reads a repeat an imported path can carry (`/accounts/{account_id}/…/accounts/{account_id}`) as before, until import's handling of it is decided. A literal brace (`/a/{{x}}`, which routing serves as `/a/{x}`) is `RIV1125` as well, since an OpenAPI path has no escape for one; 0.49.0 read it as a path parameter named `{x}`, which no request fills. A controller's attribute route has its tokens replaced by MVC's own `AttributeRouteModel.ReplaceTokens`, and its `[[`/`]]` unescaped, so a regex class written `[[a-z]]` is read as `[a-z]`. The tokens take the route values MVC hands them: `[Area]` and any `RouteValueAttribute` subclass, read from the action, the methods it overrides, the controller, and its base classes (the action's value wins). `[action]` is the `[ActionName]`, or the method's name less an `Async` suffix, and `[controller]` drops a `Controller` suffix in any case. A controller with no `[Route]` of its own takes its nearest base class's. A token nothing supplies, an unclosed `[`, and two route values keying one name on one action or controller, all of which MVC refuses at startup, are `RIV1125` rather than literal text in the path. So is a token only an attribute Rivet can't follow to constant arguments could supply, and the message says that's why. A `.Parameter<T>(name, "path", ...)` whose name matches its token only ignoring case is `RIV1123`, since an OpenAPI path parameter is matched by its exact name (G.4).
- Contract JSON (`--from`): a `routeTemplate` token with a constraint, `?`, default, or catch-all (`{id:int}`) is refused with `RIV2017`. It was written verbatim as the path key, an invalid path whose token matched no parameter. So is a `routeTemplate` routing can't read at all (`{a}{b}`, an unclosed `{`), or one carrying a literal brace (`{{` or `}}`), which an OpenAPI path key can't hold (G.4, decision 29).
- Import: an operation whose path template has a token no path parameter declares is an invalid document, refused with the new `RIV3032` naming the operation and the token. So is a path parameter with neither a `schema` nor `content`, which OpenAPI requires on every parameter. Both used to import, and generation then guessed `string` for the token (`RIV1019`, now an error); writing a string `.Parameter` for it would be exactly the guess `RIV1019` refuses (G.4, decision 36).
- CLI: `[RivetSchemaType]` on a member whose type isn't a primitive or a nullable primitive (a record, a collection, an enum, or a `[RivetScalar]` brand) stops generation with `RIV1117` instead of vanishing, and so does `.WithResponseHeader<T>(schemaType: ...)` on such a `T`. Import no longer writes one there (G.1).
- CLI: a walked type that takes the name of a `[RivetGeneratedSchema]` component is `RIV1007`; only the enum or `[RivetScalar]` brand the schema annotates may share it. An enum entry (`isEnum`) naming no enum is `RIV1122` (G.2).
- CLI: a `[JsonExtensionData]` bag System.Text.Json refuses (not a `JsonObject` or an `IDictionary<string, JsonElement|object>`, a second bag down the chain, or one beside `[JsonUnmappedMemberHandling(Disallow)]`) is `RIV1118` (G.3, G.9).
- CLI: `[JsonRequired]` or C# `required` on a member that may be omitted (`[RivetOptional]`, `[JsonIgnore(Condition = WhenWritingNull/WhenWritingDefault)]`) is `RIV1119` (G.9).
- Runtime: the JSON adapters throw `RivetContractViolationException` when a `[JsonExtensionData]` key repeats a declared member's name or the discriminator, anywhere in the payload (a `[RivetUnion]`'s variant included), since System.Text.Json would write it twice. A payload nested past the serializer's `MaxDepth`, a cyclic graph say, is left to System.Text.Json's own error at once (G.3).
- CLI: `RIV2004` is retired. A `--from` multipart endpoint whose `inputTypeName` has no definition in `types` no longer warns: rivet-ts never ships one, on purpose, and the name is only a hint for the inline body built from the params. The contract JSON schema says so (G.5).
- CLI: two endpoints that pin one component example id must agree on it. A different value, or a summary or description that contradicts one already given, stops generation with `RIV2015`; the second `$ref` used to point at the first value without a word. That includes an imported `components.examples` entry whose C# example was edited since; an unedited one, even one whose value embeds a `$ref` to an example that doesn't exist, comes back as authored. The component now carries the summary and description its examples give (G.6).
- CLI: a status key OpenAPI can't hold stops generation with `RIV1120` instead of reaching the spec as written: `.StatusKey("abc")`, `.Returns<T>("6XX")`, a `.ResponseContent(...)` key, or an `int` status outside 100–599 (`.Status(600)`, `[ProducesResponseType(1000)]`). Generation decides by the runtime's own rule, and the runtime throws on the same keys on every call that takes a status: `.StatusKey(...)`, `.ResponseContent*(...)`, `.ResponseBinaryContent(...)`, `.WithResponseHeader*(...)`, and the response example builders, as `.Returns(...)` already did. A required response header on a key like `"abc"` used to be accepted and enforce nothing. Contract JSON takes the same keys: a `statusKey` with a trailing newline, or a `statusCode` outside 100–599 (`999`, `-5`), is `RIV2017` where it used to reach the spec, and `rivet-contract-schema.json` refuses the same ones, a trailing newline included (G.10, decision 34).
- CLI: a response header named `Content-Type` (any casing) is `RIV2009`, as OpenAPI says to ignore it, and the runtime's `.WithResponseHeader*(...)` throws on it too. Use `.ProducesContentType(...)` (G.11).
- Contract JSON (`--from`): an inline object's fields and a type's properties are one definition (`tsPropertyDefinition`), and `optional` may be left off either: absent, it reads as `false` (required). A type property without `optional` used to be refused (G.13).
- CLI: a form body's parts are the members ASP.NET's form binders bind, for multipart and `.FormEncoded()` inputs alike: a package base's members and `[JsonIgnore]` members are parts, and internal members aren't. The body `$ref`s the input's component only when the component lists exactly those parts under the same names, and is spelled out inline otherwise, carrying `x-rivet-input-type`. A route token of a form input matches its member from that same list, so a member on a package base is the path parameter rather than both a token Rivet can't type and a part. A property with no public getter is no part, and no longer makes the input multipart at runtime either, since both binders list members through their getters. A get-only complex member whose initializer creates it (`Address Home { get; } = new();`) is a part on an MVC action, since MVC binds into the object its getter returns, unless its type is a positional record class, which MVC rebuilds from its constructor and throws away (an abstract record it fills in place). A non-public setter or init accessor counts as get-only, to both binders. On a contract it's `RIV1100`, since the form mapper can't set it, and `--check` reads it the same way. `--check` also no longer reports a member MVC fills in place as a type MVC can't create, since MVC hands it the value the getter returns rather than creating one. A struct member bound through a property, settable or get-only, is `RIV4006` for the reason that holds: the request succeeds, but MVC sets none of a struct's properties, so the handler never sees what the request sends for it (a settable one used to be blamed on MVC not creating it, and a get-only one was reported as unbound). A form body states no `additionalProperties`, since the form binders neither fill a `[JsonExtensionData]` bag nor refuse an unbound field: an input with either is spelled out inline, where it used to inherit the record's `{}` or `false`. An inline body whose input record is itself a component pins the name import will give it, rather than the record's name, which import gives the component: `{Op}Request`, or the first of `{Op}Request_2`, `{Op}Request_3`, and so on that no component holds, as when the input record is itself named `AddCommentRequest`. In contract JSON a `.FormEncoded()` input's fields are `formField` params with `bodyPropertyName`, not one `body` param (G.14, decision 33).
- CLI: a form part's name is what the form binders read, not the JSON surface. `[JsonPropertyName]` on a form input member no longer renames its part, because no binder reads it, and the part takes the C# name (camelCased). To send a part under another name, give the member `[DataMember(Name = "x")]` (the minimal-API form mapper) and `[FromForm(Name = "x")]` (MVC; on a positional record, on the parameter). A contract with only one of them, or a form member with its own `[FromQuery]`/`[FromRoute]`/`[FromHeader]`/`[FromBody]`, stops generation with `RIV1100`, since no single part name reaches both hosts. So does a member only one host skips (MVC's `[BindNever]` or `[BindingBehavior(BindingBehavior.Never)]`, on the member or its class, or a class-level `[Bind]` include list that leaves it out; the form mapper's `[IgnoreDataMember]`), a type a host can't create (MVC can't create a struct or record struct, even one that declares a public parameterless constructor, or an abstract class, and needs a class to have a record's one exactly matching constructor or a public parameterless one, so each of those, which it answered with a 500, is refused; the form mapper binds nothing on a type with two public constructors or on an abstract one), and a file member nothing can set, which would make the body multipart for a part no binder reads. A get-only collection such as `List<IFormFile> Files { get; } = [];` is a part on an MVC action (a non-public setter or init accessor counts as get-only, to both binders), since MVC fills the list the getter returns, but only when the getter hands back a live, writable one: an auto-property initialised with a collection expression or `new` of a type that isn't read-only or immutable. One left null, computed on each read, or started as a read-only collection gets nothing from MVC, so a file member like that is `RIV1100`, and `--check` reads it the same way. On a contract even the live one is `RIV1100`, because the form mapper can't set it (decision 33).
- CLI: on a contract, a positional record's constructor-bound form parts are `required`, even when `[RivetOptional]` or nullable. The minimal-API form mapper refuses a request missing any constructor parameter, while MVC binds it as null, so sending every one is what both hosts accept. Such a body is spelled out inline instead of `$ref`ing the record's component, which still calls the member optional. An instance `[RivetEndpoint]` method (MVC only) keeps the member's optionality; a static one (the form mapper only) requires them too (decision 35).
- CLI: a `[FromForm]` record parameter on a `[RivetEndpoint]` method is described by its members under the names its one host reads: an instance method is an MVC action (a `Name =` on the parameter prefixes them, `p.title`, and only the members its parameter's and its class's `[Bind]` include lists both name are parts), and a static one is a minimal-API handler, read by the form mapper (`[DataMember(Name)]`, never a prefix). A record carrying an `IFormFile` makes the body `multipart/form-data`; it used to be an urlencoded `$ref` with a binary property (decision 33).
- CLI: a `[RivetRequestBody(typeof(X))]` urlencoded form body lists `X`'s members as the form binders read them, as any other form body does, so `[JsonPropertyName]` on an `X` member no longer names its part, and the body `$ref`s `X`'s component only when that lists exactly those parts. It used to be one `body` of `X` under its JSON names. An input that carries files still decides the parts, and an `X` carrying a file under an input that carries none is `RIV1022`, since the input alone makes a body multipart.
- Contract JSON (`--from`): a `formField` param's `style` must be `form`, `spaceDelimited`, `pipeDelimited`, or `deepObject`, the styles OpenAPI's Encoding Object holds, which is where a form field's style goes. Anything else (`matrix`, `label`, or `simple`) is `RIV2017`, and `rivet-contract-schema.json` refuses it too.
- Import: an imported record whose schema says `additionalProperties: false` is `[JsonUnmappedMemberHandling(Disallow)]`, so the host refuses an unknown member as the spec does. It used to accept and drop it. A form body's record is the exception for now: the form binders don't read the attribute, so they still drop an unknown part. A closed schema that contradicts itself (one another record extends, an `allOf` composition or a component an `allOf` composes, a polymorphic variant, a `oneOf` or `anyOf` union with a variant that can be an object, or a generic template instance whose template serves open instances too) stays open with the new warning `RIV3033`, which names it by its component key, or by its pointer when it's inline, and says why. A variant stays open because System.Text.Json reads its discriminator, which the record leaves to the base, as an unknown member whenever the variant is read on its own. A `oneOf` or `anyOf` whose every branch is empty or says only `type: object` adds nothing to the object it sits on, so that object imports as its own record, members and closure included, instead of a union wrapper that dropped both (Vercel's `connectConfigurations` item); the spec keeps the composition as written. An inline `{"type": "object", "additionalProperties": false}` with no properties still imports as a `Dictionary<string, JsonElement>`, which takes any member, so the host doesn't refuse one yet; the spec still says `additionalProperties: false`.

#### Fixes

- CLI: a route token declared with `.Parameter<T>(name, "path", ...)` on a GET or DELETE input that lacks the property no longer draws `RIV1019` (G.4).
- CLI: a generic instantiation that only a template's members reach (`PagedResult<X>` inside `Wrapper<X>`) claims its component name like every other one, so a synthesized tagged-union variant can't land on it, and `RIV2001` no longer blames a pinned id nobody wrote (G.12).
- CLI: `"DEFAULT"`, `"Default"`, and the like are emitted as OpenAPI's `default`. The runtime already accepted any casing (G.10).
- Attributes: `[RivetFormat]` goes on a struct, so a `[RivetScalar] record struct` brand carries a format as a class brand does, and `RIV1117`'s advice to put one there can now be followed (G.1).
- CLI: a file on a base class from a NuGet package is a part of its multipart body. It used to make the body multipart without being listed, so clients couldn't send it. An `internal new` member of a package type hides its base's file, as it does at runtime (G.14).
- CLI: a contract whose declared request content is a form (`.RequestContent<T>("multipart/form-data")`, as `--from-openapi` writes a multipart body with no file in it) lowers its input to form fields, which is how the runtime already bound it. It used to be one JSON `body` param, so `--check` expected a `[FromBody]` handler (decision 33).
- CLI: a request example on a form body with form fields and no files defaults to `application/x-www-form-urlencoded`, the body's own media type, instead of a second, `multipart/form-data` content entry (decision 33).
- Import: a multipart or urlencoded body whose part names aren't their property names (`file_name`, `x-meta`) is written with `[DataMember(Name)]` and `[FromForm(Name)]` beside `[JsonPropertyName]`, so an imported server actually receives those parts. Every form input record, a multipart body with no binary part included, is written in the `{ get; init; }` form, since the minimal-API form mapper refuses a request missing any positional constructor parameter, nullable or not (decision 33).
- Import: a source's response header named `Content-Type` no longer becomes a `.WithResponseHeader(...)` (which generation now refuses and the runtime would demand); it comes back verbatim on re-emit, a Swagger 2 source's under `schema` as OpenAPI 3 writes it, and so does one on a response the source `$ref`s from another operation. Only what OpenAPI ignores comes back: a response whose only other header is one import drops (an empty name) no longer brings that header back beside it (G.11).
- Import: a request body the source `$ref`s from another operation, rather than from `components/requestBodies`, keeps its media `encoding` on emit, as such a response does.
- Import: Rivet's own empty record with a bag (`x-rivet-empty-record` beside `additionalProperties`) re-imports as a record, not a dictionary, and a source schema that writes `additionalProperties: {}` comes back from import and emit with `additionalProperties: {}`; it used to come back without it (G.3).
- Import: a `$ref` to a component that admits null is nullable when the component is an empty record or a dictionary, as it is for any other record. A `$ref` to a nullable `oneOf` object, properties beside it or not, names the type its `oneOf` holds, as a property or a `oneOf` variant, and one to an `allOf` object that declares no properties of its own, beside `additionalProperties`, names the record its elements merge into; they used to name a record nothing wrote (which didn't compile) or a dictionary. A `oneOf` or `anyOf` of null and a value beside a `type` is the value's type when the value says what it is (a `$ref`, its own type, properties, or items, or an `enum`), nullable only when that sibling `type` admits null; it used to be the sibling `type` alone (a dictionary for an object, the scalar for a string). A value with only a format or a bound still leaves the sibling `type` to name it.
- CLI: a contract-JSON form field's `style`, `explode`, and `allowReserved` go in the form media type's `encoding`, and its named examples' values join the field's schema `examples`. They used to be dropped silently. A field with examples spells its form body out rather than `$ref`ing the input record's component, which every operation naming it shares, so the examples join the part's schema there too. The encoding is written for multipart and urlencoded bodies alike. What a form field can't carry (an example's summary, description, or `externalValue`, an example that is only `externalValue` or `$ref`, or `allowEmptyValue`) is the new warning `RIV2019`.
- Import: an operation with a path parameter declared with `content` instead of a schema is dropped with `RIV3025`, naming it, preserved fields included, whether the parameter sits on the operation, its path item, or a path item it `$ref`s. It used to import without the parameter, leaving its route token untyped, so generation stopped with `RIV1019`. Before anything drops an operation, import inlines every `$ref`'d path item, and every parameter, request body, response, header, or example reference into `paths`, so a drop, here or for `RIV3030`, never breaks one of those or changes what another path reads, whatever order the paths come in. A schema `$ref` into `paths` stays as written. `RIV3030` used to leave a `$ref`'d path item's operations unchecked, and a `$ref`'d path item's operations now keep their provenance (component references, tags, and the like) as an inline item's do.

#### New

- CLI: route constraints become schema. `int`/`long`/`guid`/`bool`/`datetime`/`decimal`/`double`/`float` type the parameter, and declare its token on their own. `min`/`max`/`range` become bounds, `length`/`minlength`/`maxlength` become lengths, and `alpha`/`regex` become a pattern, a regex matching either letter case as routing does (G.4).
- CLI: route, query, header, and form params lowered from an input record keep the member's annotations: `[RivetDescription]`, `[Range]`/`[StringLength]`/`[RegularExpression]` and the other bounds, `[RivetDefault]`, `[Obsolete]`, `[RivetFormat]`/`[EmailAddress]`/`[Url]`, `[RivetSchemaType]`, and `[RivetExample]`. So do the `[RivetSchemaRef]`s, item metadata, and the metadata at the member's own schema (a title, schema examples) that import writes, through the one mapping a body property's schema uses; contract JSON's endpoint param takes that metadata as `scalarMetadata`, as a property does. So do `[FromQuery]`/`[FromRoute]`/`[FromHeader]`/`[FromForm]` action parameters. A form field's annotations land on its property schema in the body. A property's authored example leads its schema's `examples`, ahead of any its type carries, record properties and form fields alike, so import reads it back as the property's example rather than the type's first (G.8, decision 31).
- CLI: a type with a `[JsonExtensionData]` bag emits `additionalProperties: {}`, its own or a base's, polymorphic variants included. A type marked `[JsonUnmappedMemberHandling(Disallow)]` emits `additionalProperties: false`. An imported record keeps its source's word: its bag says `{}` when the source wrote `additionalProperties: {}`, which the importer records as `[RivetGeneratedType(..., DeclaresAdditionalProperties = true)]`, and nothing when the source left the keyword out (G.3, G.9).
- Contract JSON (`--from`): a type definition (object types only) and an inline object take an optional `additionalProperties: true | false` (G.3, G.9).
- Contract JSON (`--from`): a top-level `security` (the endpoint `security` shape) says what every operation without its own needs, emitted as the root `security`. It beats `--security`'s first-scheme default; `--security` still defines the schemes (G.7).

### Part 4: `--check` and controllers reach the rest of ASP.NET

`--check` used to know one shape of handler (a lambda written in place, returning its terminal itself), skip Azure Functions altogether, and take security on trust. It now follows method groups and the handler's own helpers, compares a function's parameters as the worker really fills them, reads form members the way each host binds them, and holds every handler's authorization up against the security its spec declares. Controllers can declare that security too.

#### Breaking

- CLI: `--check` compares each contract endpoint's security with its handler's authorization, as an error. It asks only whether a caller must authenticate. `RIV4008` reports a secured contract over a handler anyone can call, and a contract that admits anonymous callers (`.Anonymous()`, `.OrAnonymous()`, or no security at all, which OpenAPI reads as "no credentials needed") over one that requires authentication. It reads ASP.NET's own metadata: `[Authorize]`/`[AllowAnonymous]` (any `IAuthorizeData`/`IAllowAnonymous`) on the action, controller, and base controllers or the minimal-API handler; an `AuthorizeFilter` in `MvcOptions.Filters`; `RequireAuthorization()`/`AllowAnonymous()` on the endpoint, its route groups, and `MapControllers()`; the fallback policy (`FallbackPolicy =`, `SetFallbackPolicy`, or `AddFallbackPolicy`); the default policy, which a bare `[Authorize]`, `RequireAuthorization()`, or `new AuthorizeFilter()` means; and a Functions trigger's `AuthorizationLevel`. A filter or policy set in a helper applies where the helper is called, under that call's condition. A call through an interface the helper implements, or a method it overrides, counts only when the receiver is visibly an instance that runs it (`IAppModule m = new AuthModule();`); any other receiver is unknown. Setup nothing calls runs only where ASP.NET runs it: top-level statements and the entry point, in `rivet <files> --check` as in a project, since files holding top-level statements, or a `Main` the compiler takes as the entry point and builds as an app, now compile as the app they are; a Startup class's `ConfigureServices`, `Configure`, and `ConfigureContainer` where `UseStartup<T>()`, `UseStartup(typeof(T))`, or a `UseStartup(context => new T(...))` factory hands it over, the most-derived one only, so a base method the Startup overrides or hides doesn't run (an environment's own `Configure{Env}…` runs only in that environment, so either is unknown, and a `UseStartup` whose type can't be read makes every public `Configure…` method unknown); and an `IConfigureOptions<T>` or `IPostConfigureOptions<T>` class registered under that interface, by `ConfigureOptions<T>()` or a service registration whose service type is the interface (`AddSingleton<T>()`, a `nameof`, or a field of that type registers nothing). Setup in a constructor, a property, or a field initializer is unknown. A local function that applies a requirement to a builder it captures counts under each call's condition, and applies nothing when nothing calls it. A public `Configure…` helper nothing calls no longer counts as run. A default policy set only under a condition is decided when every branch requires a user, as ASP.NET's own default does, and a `return` above a local function's declaration no longer makes the function's requirement conditional. Custom authorization filters and middleware are invisible. When the document declares no security scheme at all, every handler that requires authentication under a contract that says nothing is one `RIV4008`, telling you to declare the default in source. Every operation declared with attributes is compared against its `[RivetSecure]`-family attributes too: `[RivetEndpoint]` methods (a static one at each `Map*` call that names it), `[RivetClient]` controllers' actions, and overrides of an abstract `[RivetContract]` method, against the contract method's. A handler that serves several contract fields is compared under each. A named policy (`[Authorize(Policy = "X")]`, `RequireAuthorization("X")`, or `new AuthorizeFilter("X")`) requires what its registration requires (`AddPolicy` on `AuthorizationOptions`, or `AddPolicy`, `AddDefaultPolicy`, or `AddFallbackPolicy` on `AddAuthorizationBuilder()`), looked up ignoring case as ASP.NET does, so a policy that admits anyone doesn't count as requiring authentication, and `RIV4008` names that policy rather than asking for the `[Authorize]` the endpoint already has. A policy whose only requirement is `RequireAssertion(_ => true)` (beside `AddAuthenticationSchemes` or not) admits anyone, inline or registered. A policy holding a user requirement (`RequireAuthenticatedUser`, `RequireRole`, `RequireClaim`, or `RequireUserName`) requires a user whatever else it holds, an assertion or a requirement `--check` can't read included, though in a configure lambda only where that requirement always runs. Any other assertion is unread. Policies on one endpoint combine as ASP.NET combines them, so one that requires a user decides it, and roles decide an `[Authorize]` whatever its policy, a blank `Roles` included (ASP.NET then lets nobody in), while a blank policy name is no name. The host rules `--check` follows (`[AllowAnonymous]` over an `[Authorize]` controller, a global `AuthorizeFilter`, a group's `RequireAuthorization()`, and the fallback; the fallback only over an endpoint with no authorization of its own; a minimal API's handler method's attributes but not its class's; named policies, including the name `AddFallbackPolicy` registers) are pinned on a real host, each "beats" rule beside the requirement it beats (K.5).
- CLI: authorization setup `--check` can't read statically is the new `RIV4009`, an error, naming each site: a requirement applied only under a condition, a policy it can't follow, a convention on a builder it can't trace to its `Map*` call (a delegate's answer, what an interface or abstract method returns, or what a call without source returns when it's handed a builder; one that maps endpoints of its own, like `MapHealthChecks`, returns no route builder and covers only those), or a `Map*` call on a builder it can't trace to its `MapGroup` or the app (a field, a group parameter nothing passes, or what a helper without source returns). Builders are traced as they are for routes (below), so a `this IEndpointRouteBuilder` helper called on a group sees that group's `RequireAuthorization()`. A named policy without a registration it can read is `RIV4009` too: one nothing registers, one registered only under a condition, one whose policy comes from config or a variable, and every name once a policy is registered under a name it can't read or the app registers an `IAuthorizationPolicyProvider`. So is an `IAuthorizeData` attribute of your own that takes constructor arguments, since its constructor may set a policy or roles `--check` doesn't see. It's never a guess: an endpoint every reading agrees on (an `[AllowAnonymous]` action under a conditional `RequireAuthorization()`, say) is decided. Sites under one condition share one unknown, so `RIV4009` fires only when the condition itself decides the endpoint, and an endpoint decided across a condition's branches names each site under it: two sites share one when they sit in the two branches of one `if` or `?:`, or each reads the same `const`, `static readonly` field, or local with one known value, and a lone conditional fallback policy that requires a user joins them. A condition inside a method counts only between a requirement and the group or endpoint the same method makes, and app-wide setup correlates only in top-level statements or the entry point, which run once. A conditional filter or policy in a method nothing calls sets nothing (K.5).
- CLI: `--check` compares an Azure Functions handler's parameters with its contract (`RIV4006`). The worker fills an unattributed parameter by name, from a route value, else the query, else a JSON body's top-level property, so a parameter named after no declared route token, query parameter, or body property is now an error: it's always `null`. One named after a declared header, cookie, or form field is reported too, since the worker never reads those. The contract carries a JSON body's property names for this (`BodyFieldNames`), a body declared only by `.RequestContent<T>("application/json")` included, so a misspelt parameter on a JSON-body POST no longer slips through. Such a body keeps every member of `T` that isn't read-only in that list, one sharing its name with a route-bound input member included (K.2, decision 32).
- CLI: `RIV1115` is now "MVC binding setup that can't be read statically". Beside a `SuppressInferBindingSourcesForParameters` that isn't a constant, a property filter other than `[Bind]`'s include list (any other `IPropertyFilterProvider`), or a `BindingBehaviorAttribute` subclass that sets its own behaviour, on an MVC parameter, the type it binds, a member, or a contract's form input type, stops generation and `--check` with it, since MVC runs its code to choose the members it binds. A minimal-API-only check never reads them. The constant is now `Diagnostics.UnreadableMvcBindingSetup`.
- CLI: a contract and a `[RivetEndpoint]` action at the same method and route merge only when they declare the same security; otherwise it's `RIV2012`, naming both sides' security when that's the only difference, as it does for two such operations in contract JSON. Its advice is in the terms each side declared its security in: builder calls on a static contract's field, and attributes on an abstract contract's method or an action. A pair that shares one spelling is told to give both the same steps, a mixed pair is told which side uses which, and `--from` contract JSON is told to align the endpoints' `security` field, so it no longer gets C# attribute advice. One side's security used to be dropped silently (K.3).

#### Fixes

- CLI: `--check` follows a minimal API handler that isn't written in place. A method group (`app.MapGet(route, TaskHandlers.Get)`), a local function, or a local holding a lambda is the route handler, exactly as a lambda is. Its terminals cover the field, a `.Bind` in it is no longer a false `OrphanedBinding`, and its parameters are what `RIV4005` and `RIV4006` read. One handler mapped twice is checked at each mapping, each with its own route and its own body inference, so a method group mapped with both `MapPost` and `MapGet` has its unattributed array read as a body on one and a query parameter on the other (K.1).
- CLI: `--check` follows the handler's own helpers. A terminal handed to a helper with source in the project covers the field when the helper returns the host's adapter applied to it, as in `Done(endpoint.Success(x))` with `Done(r) => r.ToResult()`, through any number of helpers. A helper that drops the terminal or adapts something else still covers nothing (K.4).
- CLI: a handler that reads `Request` (or `RouteData`) through a method or property it calls with source in the project is trusted to read its inputs by hand, so `RIV4006` no longer says it "never binds" them. That covers a controller's own helper, an extension handed `this`, and a static helper handed an `IHttpContextAccessor`, as deep as the calls go. A helper with source counts only when its own body reads the request, so an `Audit(HttpContext)` that reads only `User` no longer hides a declared input; a method only a package knows is still judged by what it's handed (K.4).
- CLI: `RIV4005` on Azure Functions names query values as well as route values: the worker parses both as JSON, so an enum's member name never binds, quoted or not. A real-host test now pins this (K.2).
- CLI: on a minimal API, `--check` reads a `[FromForm]` record the way the form mapper binds it. Every member is a form field under its C# name or its `[DataMember(Name = ...)]`, never under a member's `[FromForm(Name = ...)]` or `[FromQuery]`, which the mapper ignores (K.6).
- CLI: `--check` reads an `[AsParameters]` type as the minimal-API host binds it. With a parameterised constructor, only the constructor's arguments bind. A type the host refuses at startup (an abstract one, several constructors and no parameterless one, or a constructor parameter no property matches) is `RIV4006`, since the endpoint never serves a request. So is a type MVC binds but can't create, which fails the request, and a `[FromForm]` type the minimal-API form mapper binds nothing on; their members are still compared as the host would bind them. An `[ApiController]` action's unattributed struct whose members carry their own binding sources is compared member by member, as MVC infers it (K.6).
- CLI: `--check` reads MVC's `[Bind("A", "B")]` include lists, `[BindNever]`, and `[BindingBehavior(BindingBehavior.Never)]`, so it no longer reports a member MVC never binds. A parameter's list and its class's both apply, since MVC runs both filters; a nested member's class's own list applies wherever it's bound; a class-level `[BindNever]` (a base class's included) skips every property that carries no behaviour of its own, as does a `[BindNever]` on the base property an override overrides; and a positional record's constructor parameter that its own `[BindNever]` or a list leaves out isn't bound: MVC constructs the record with its default. A class-level `[BindNever]` doesn't reach a constructor parameter, since MVC reads a parameter's behaviour from the parameter alone.
- CLI: an `[ApiController]` action's unattributed complex parameter is a body unless one of the properties MVC's metadata lists for it carries its own binding source, whatever its setter, `[BindNever]`, or `[Bind]` list says; a positional record's constructor parameters aren't among them. So a record whose only `[FromQuery]` or `IFormFile` member is a constructor parameter is a body, as MVC infers it, and a `[FromQuery]` property stops the inference even when it's get-only or `[BindNever]`. `--check` used to read the members MVC binds instead.
- CLI: on MVC, `--check` reads the model name from `[Bind(Prefix = ...)]` on a parameter, its class, or a base class (as reflection hands it to MVC), and from a member's `[BindProperty(Name = ...)]`, as well as from `[From*(Name = ...)]`, so those prefixes and renames are compared like the rest. A positional record's members are read from the constructor parameter's attributes, as MVC does, so a `[property: FromForm(Name = ...)]` MVC never sees no longer renames one there, and a `new` member of any accessibility hides its base's, as it does for the contract (K.6, decision 33).
- CLI: a `MapGroup` local that carries a convention, as in `var api = app.MapGroup("/api").RequireAuthorization();`, keeps its prefix, so `api.MapGet("/items", …)` is checked as `/api/items` rather than reported as a `RouteMismatch` (K.5).
- CLI: `--check` follows a local in a top-level `Program.cs`, so `var group = app.MapGroup("/v2"); group.MapGet(…)` and a contract field held in a top-level local resolve there as they do inside a method (K.5).
- CLI: `--check` traces a minimal-API builder one way for routes and for authorization: through locals, conventions, and route-group helpers' parameters and return values. So `app.MapGroup("/todos").MapTodos()` keeps its prefix, a helper called from two groups is checked at both (and a warning about one of them says which), a helper that makes its own group or endpoint is a separate mapping at each call, so a requirement on what one call returns covers that call's endpoints, and a helper that returns a new group (`g.MapGroup("/v2")`) is no longer taken for the group it was handed. A `Map*` call on a builder it can't trace (a field, a group parameter nothing passes, what a helper without source returns, or a group a helper nests by calling itself) leaves the route unresolved, rather than comparing it as if the group had no prefix. An `IEndpointRouteBuilder` parameter nothing in the project passes is still read as the app, as a framework-invoked `AddRoutes(app)` is; an `IEndpointRouteBuilder` field no longer is (K.1).
- CLI: `rivet <files>` over files holding top-level statements compiles and generates, instead of stopping on `CS8805` ("Program using top-level statements must be an executable"): the files compile as the app they are, as do files with one `Main` the compiler takes as the entry point and builds as an app. Files it can't build as one app (two `Main`s it could take, an `async void Main`, or a lone `Main` without an entry-point signature) still compile as a library and generate as before (K.5).

#### New

- Attributes: `[RivetSecure(scheme, scopes...)]`, `[RivetAndSecure(...)]`, `[RivetOrAnonymous]`, and `[RivetAnonymous]` declare security on a `[RivetEndpoint]`/`[RivetClient]` controller or action (and a `[RivetContract]` abstract method). They mean what `.Secure()`, `.AndSecure()`, `.OrAnonymous()`, and `.Anonymous()` mean and contradict the same way (`RIV1114`). The action wins over its controller, and the controller over its bases. ASP.NET's `[AllowAnonymous]` alone reads as `[RivetAnonymous]` (K.3).
- Samples: `samples/ContractApi` declares its security in source (`[assembly: RivetSecurityScheme]` and a bearer default) and authorizes what its contract secures, over a demo bearer scheme that takes any token from the header or the `.QueryAuth()` query parameter, and refuses to start outside Development. Plain generation and plain `--check` are clean, with no `--security`. The avatar endpoint is implemented and `.Secure("bearer")`, and the health check is the minimal API, on the contract's own route (K.5, decision 37).
- Samples: `samples/FunctionsApi` gains a JSON endpoint with an enum route value and an enum query parameter, and `task test:functions` pins what the isolated worker binds into a function's parameters (K.2).
- Docs: the required-response-header rule says why a header middleware adds in `OnStarting` still doesn't count: the callbacks run last-registered-first, so the only fix is a first-registered `UseRivet()` middleware in every host (§E.3, decision 9).

### Part 5: the gate and the diagnostics registry

A diagnostic's severity used to be decided twice, once at the call site and once in a docs column kept by hand, and around fifty user-facing errors had no ID at all, so the one thing you could grep for was the message text. Severity now lives in the registry and nowhere else, and every error Rivet stops on, except a command-line usage error, carries an ID, one per family, with a docs row that says what to do about it. A crash that can only mean a Rivet bug says so with a stack trace instead of dressing up as your mistake.

#### Breaking

- CLI: every error Rivet stops on, except a command-line usage error, carries an ID, so messages that began `error:` now begin `error RIVnnnn:`. Invalid `[RivetSecurityScheme]`/`[RivetOAuthFlow]` metadata is the new `RIV1121`; an authored value that isn't the shape its slot needs (a builder argument's JSON, a `[RivetDefault]`/`[RivetExample]` value, a `.Parameter<T>()` location) is `RIV1123`; an unreadable `host.json` is `RIV1124`; C# that doesn't compile is `RIV1126`, which replaces the closing "Aborting — cannot proceed with compilation errors." line; a `[RivetPreservedField]` that can't attach to its emitted owner is `RIV2016`; an invalid `--security` value is `RIV2018`, and so is a scheme definition or a second value for `--from-openapi`'s `--security`, which takes one scheme name (it used to print the usage after it); a `--verify` that finds the committed spec missing or stale is `RIV2020`; a `--from` or `--from-openapi` file that doesn't exist is `RIV2021`; and an invalid `--from-openapi` document is `RIV3032`. Malformed generated or provenance metadata is `RIV1122` everywhere, invalid `--from` contract JSON is `RIV2017` everywhere, and `.AcceptsBinary()` beside `.AcceptsFile()` or `.FormEncoded()` is `RIV1104`. Nothing that used to pass fails now (T.2).

#### Fixes

- CLI: a diagnostic's severity is decided once, in the registry. A warning ID can no longer be thrown as an error, nor an error ID printed as a warning. `--check` takes each result's `warning`/`error` word from the registry, and the test suite holds the reference page's Severity column to it (T.1).
- CLI: JSON that doesn't parse inside a generated attribute (`[RivetGeneratedSchema]` metadata, a `[RivetOperationProvenance]` schema, a request-body example's referenced components) or in a builder's `referencedComponentsJson` is `RIV1122` or `RIV1123`; it used to crash with a `JsonException` stack trace (T.2).
- CLI: the sites that can only fire on a Rivet bug (an unsupported security scheme model, and a preserved field or component whose JSON the walker already checked) throw `InvalidOperationException`, and `RivetUserException`'s constructor is private, so every one is built through the registry and carries a registered error ID (T.2).
- CLI: an OpenAPI provenance attribute with the wrong number of arguments, which means a `Rivet.Attributes` of another version than the tool, is `RIV1122` naming both counts and the version mismatch, instead of an `IndexOutOfRangeException`. Re-importing alone can't cure it. A shorter `[RivetGeneratedSchemaMetadata]` from an older version reads its missing numeric bounds as absent instead of crashing, as its other fields already did, and a `[RivetSecurityScheme]` missing its type is `RIV1121`. A preserved `headers` field is accepted only on an operation response, where import writes it (T.2).
- CLI: a source file or `--project` path that doesn't exist is `RIV2021`, naming it. A machine where Rivet finds no MSBuild, a `--project` file MSBuild can't open as a C# project (a `.sln`, an `.fsproj`, or a stray file), or a project that yields no compilation is `RIV1126`. Each used to crash with a stack trace.
- Import: a component example with neither `value` nor `externalValue`, only a summary or a description, imports and comes back as written. OpenAPI makes both optional and only refuses the two together, so `RIV3032` now stops on both and nothing else; it used to stop on neither too (T.2).
- CLI: an apiKey location, in `--security apikey:<in>:<name>` or `[RivetSecurityScheme(location: ...)]`, must be `query`, `header`, or `cookie` by name. A number used to slip through `Enum.TryParse`, so `1` quietly meant `header` and `7` wrote `"in": "7"`; it's `RIV2018` or `RIV1121` now.
- CLI: a `[RivetSecurityScheme]`, `[RivetOAuthFlow]`, `[RivetGlobalSecurity]`, or `[RivetGlobalSecurityScheme]` whose arguments Rivet can't read (a null name, flow, or scope list, or arguments from another `Rivet.Attributes` version) is `RIV1121`, naming the attribute. So is a `[RivetOAuthFlow]` for a scheme that isn't a declared `oauth2` one, and a `[RivetGlobalSecurityScheme]` whose alternative no `[RivetGlobalSecurity]` starts. Each used to be skipped, so its scheme, flow, or requirement dropped out of the spec without a word. A null scope used to read as an empty one, and a scope or flow declared twice crashed with no ID; all of these are `RIV1121` now (T.2).

#### New

- CLI: `--tool-version` prints Rivet's own release (`0.50.0`, without the `+commit` build metadata) and exits `0`. `--version` still sets the spec's `info.version`. rivet-ts runs it to refuse a `rivet.binaryPath` binary too old to read the contract JSON it writes, and the release smoke test checks that it prints the tag's version.

## 0.49.0 — 2026-10-26

The gap-audit release. Every place where Rivet knew it was wrong and wrote it up in the docs instead of fixing it, it now either gets right or refuses. That means a lot of former warnings now stop generation, so expect `dotnet-rivet` to fail on contracts it used to wave through. Each error names the thing and says what to do instead. It comes in three parts: wrong specs that used to ship silently, promises nothing checked, and the binding, security and corpus work that finishes the job.

### Part 1: wrong specs no longer ship silently

#### Breaking

- CLI: a header's or parameter's `exampleJson`, `examplesJson`, `schemaExamplesJson` or `metadataJson` that isn't the JSON it should be stops generation, naming the header or parameter and the endpoint (and, for JSON that doesn't parse, the argument). Schema examples must be an array, and `examples` a map of named Example objects, from C# and from `--from` contract JSON alike (`rivet-contract-schema.json` now says so too). Malformed JSON used to crash with a stack trace, and the wrong shape went into the spec as written.
- CLI: a `[JsonConverter]` Rivet can't model is refused with `RIV1111`. That's one on a walked type (other than `[RivetScalar]` and `[RivetUnion]`), or one on a property or field. The spec used to describe the CLR shape while the converter wrote something else entirely. On a primitive-typed property, `[RivetSchemaType("string")]` pins the wire and is accepted. An enum converter belongs on the enum type.
- CLI: `[JsonNumberHandling]` with `WriteAsString` or `AllowNamedFloatingPointLiterals` on a number, from the property or from the type being serialized, is refused with `RIV1112`. That covers `Int128`, `UInt128` and `Half`, and a generic's `T` member wherever an instantiation binds it to a number (`Wrapper<int>` is refused, `Wrapper<string>` is fine). It puts strings on the wire where the spec says number. `AllowReadingFromString` alone is fine: numbers are still written as numbers, and the host just reads a little more generously.
- CLI: two types that share a simple name now stop generation with `RIV1007`, naming both. That covers different namespaces, nested types with the same name, and `Result` beside `Result<T>`. Before, the second one walked was quietly emitted as `Item2`, so a schema name depended on discovery order. Rename one of them.
- CLI: `BigInteger` is refused with `RIV1010`. System.Text.Json has no converter for it: it writes the struct's `IsZero`/`Sign` properties and can't read them back. Use a string of digits, or `long` or `decimal`.
- CLI: a `[JsonDerivedType]` with an int tag or no tag is refused with `RIV1014`. The base used to fall back to flattening, which describes a payload System.Text.Json never writes.
- CLI: a `[RivetUnion]` with no variant properties is refused with `RIV1018` instead of being flattened.
- CLI: a contract endpoint field that isn't `static readonly` stops generation with `RIV1001`. Rivet reads the initializer, so a field that can be reassigned, or exists once per instance, could serve something different from the spec. Declare it `public static readonly`.
- CLI: a contract endpoint field Rivet can't read stops generation with the new `RIV1113`: no initializer, an initializer that isn't a `Define.*` chain (a helper call, another field), an endpoint declared as a property, a call that isn't a Rivet builder method, an example with nothing in it, a `null` route, or any string, int or bool argument that isn't a compile-time constant. Each refusal says how to fix that case. Rivet used to skip such a field, so the operation vanished from the spec without a word. A variable passed to a builder call fared no better: `.Summary(text)` was skipped, `.Status(code)` fell back to the default status, `.ProducesFile(type)` to `application/octet-stream`, `.QueryAuth(name)` to `token`, and `.Secure(scheme)` dropped the endpoint's security. The "not a Rivet builder method" refusal had no ID before; it's `RIV1113` too.
- CLI: a response example for a status the endpoint never declares stops generation (`RIV1002` for contracts, `RIV1004` for controllers). The spec had nowhere to put the example, so it used to vanish with a warning. Declare the status, or fix the example. A status declared only by `.ResponseContent(...)` counts, for examples and headers alike. An example without a media type takes that status's own, or the success body's `.ProducesContentType(...)`/`[Produces]`, instead of adding an undeclared `application/json` entry; one naming an undeclared media type is refused.
- CLI: `.WithResponseHeader()` on a status the contract doesn't declare stops generation with `RIV1017`, rather than leaving out a header your handler sends.
- CLI: a dictionary, collection or scalar input on GET, DELETE or `.AcceptsBinary()` stops generation with `RIV1020`. It used to drop the input and carry on as if the endpoint took nothing. Use a record with one property per route or query parameter, or move the values into a JSON body.
- CLI: two `[ProducesResponseType]` on the same status fail generation with `RIV2010`. Rivet used to keep the first and drop the other's body.
- CLI: malformed `--from` contract JSON is refused (exit 1) instead of quietly degraded: a generic with no template (`RIV2007`), one brand declared two ways (`RIV2008`), a repeated response status (`RIV2010`), an unbound type parameter (`RIV2006`), a `$ref` to a type the contract never ships (`RIV2005`), a name declared twice across types and enums, and an enum without exactly one of `values`/`intValues`. The last two used to crash or let the last one win.
- CLI: an unmapped C# type, or an `unknown` primitive whose `csharpType` names a type with no schema mapping, fails with `RIV2005` instead of shipping an untyped `{}`. "Any JSON value" (TypeScript `unknown`, `object`, `JsonElement`, `JsonDocument`, and the `JsonNode` family including `JsonValue`) still maps to `{}`, now with no diagnostic at all.
- CLI: a preserved component whose own `$ref` dangles (the source OpenAPI was broken) fails emission with `RIV2005`, naming the component and where it's referenced. Rivet used to invent an untyped stand-in. The check runs over the finished document, so a preserved field such as an `encoding` header is covered, and a `"$ref"` key inside an example's `value`, a link's `requestBody` or `parameters`, or a default, const, enum or `x-` extension is data, not a reference.
- CLI: a `[RivetEndpoint]` method or an abstract `[RivetContract]` method with no HTTP verb, or an endpoint (`[RivetClient]` included) with no route template on the action or its class, stops generation with `RIV1100`. It used to vanish from the spec.
- CLI: a type with more than one `[JsonConstructor]` constructor stops generation with the new `RIV1116`. System.Text.Json refuses it at runtime.
- CLI: a generic used with more type arguments than its template declares fails with `RIV2006`. The extra arguments used to be dropped.
- CLI: two routes that differ only in parameter names (`/tasks/{id}` and `/tasks/{taskId}`) stop generation with the new `RIV2013`. OpenAPI reads them as one path, and Rivet used to write both keys into an invalid document.
- CLI: `RIV2001` fires only for a producer-pinned `componentId` that lands on a different schema, and it's an error.
- `Rivet.Attributes`: `RivetVendorExtensionAttribute` is now `RivetPreservedFieldAttribute`, because it carries documentation fields as well as `x-` extensions. Re-import to regenerate.

#### Fixes

- CLI: `TimeSpan` maps to the string System.Text.Json writes, the invariant `"c"` format (`[-][d.]hh:mm:ss[.fffffff]`), with a matching `pattern` and `x-rivet-csharp-type: TimeSpan`, including as a dictionary key. It used to be an untyped `{}` with `RIV1009`, which is retired.
- CLI: `Int128`, `UInt128` and `Half` map to the numbers System.Text.Json writes (`integer`, `integer`, `number`, each with `x-rivet-csharp-type`). They used to be `{}`.
- CLI: a DataAnnotations constraint on a positional record parameter without `[property:]` now reaches the spec. That's where MVC validation reads it, so the spec used to be looser than the wire. `[RivetConstraints]` can sit on the parameter too. A derived record's parameters are read from its own constructor, so a base record's attributes don't leak in.
- CLI: a record's get-only property bound by its primary constructor is no longer marked `readOnly`. Rivet never recognised the primary constructor, but System.Text.Json reads the property through it. `readOnly` now follows System.Text.Json's own constructor choice: `[JsonConstructor]`, else a struct's default constructor, else a class's public parameterless constructor, else its only public constructor.
- CLI: a tagged-union variant whose `{Base}_{Tag}` name is already taken, or whose tag PascalCases like a sibling's, gets a numeric suffix and `$ref`s its own schema. It used to point at whoever owned the name.
- CLI: `--from-openapi` no longer drops things without saying so, and carries most of them through instead. Path-item `summary` and `description`, operation `externalDocs`, response and component `links`, media-type `encoding`, `info.summary` and `jsonSchemaDialect` ride along as preserved fields and come back out at the same pointer. A query parameter's `allowReserved` is imported and emitted. What still can't be carried is reported: a parameter with `content` instead of a `schema` (`RIV3025`), callbacks (`RIV3027`), and webhooks and `components.pathItems` (`RIV3028`).
- CLI: a response header with an empty name, or a second spelling of one already declared on that status (`X-Rate` and `x-rate`), leaves a `[rivet:unsupported header …]` marker instead of quietly disappearing.

### Part 2: promises Rivet now checks

#### Breaking

- `Rivet.Attributes`: `.ToResult()` and `.ToActionResult()` refuse host JSON options that would put a different wire on the spec. The spec assumes System.Text.Json's web defaults, so another naming policy, a `DictionaryKeyPolicy`, anything in `Converters` (Rivet's own enum converters included), `NumberHandling` that writes strings, an ignore condition, `IgnoreReadOnlyProperties`/`Fields`, `IncludeFields`, a `ReferenceHandler`, `UnmappedMemberHandling.Disallow`, `RespectRequiredConstructorParameters`, or a resolver that isn't the default one or a source-generated context now throws `RivetContractViolationException` naming each difference. Before, the docs called all this "invisible to the spec" and shipped the wrong spec anyway. Declare the behaviour on the types instead. So is a source-generated context declared with `[JsonSourceGenerationOptions(UseStringEnumConverter = true)]`, which builds the string converter into each enum it covers where the options never show it. Settings that only loosen reading or change formatting (case-insensitive names, trailing commas, indenting, the encoder) are left alone. Each options instance is frozen and compared once; they're final once `IOptions` has resolved them.
- `Rivet.Attributes`: polymorphism added through `TypeInfoResolver` modifiers is refused with everything else above. 0.45.0 accepted it, but the spec never showed the `$type` or the extra members. Use `[JsonPolymorphic]`/`[JsonDerivedType]`.
- `Rivet.Attributes`: a response header declared `required: true` is checked. A response at that status written without it throws, naming the header and the status. Set it on `HttpContext.Response.Headers` before returning; a file's `entityTag:`, `lastModified:`, `downloadName:`, `inline:` and `enableRangeProcessing:` count for the headers they produce, and a text body counts for `Content-Length`. A header a middleware only adds in `OnStarting` arrives too late to count.
- `Rivet.Attributes`: the Rivet enum converters read exactly the names the spec lists, case-sensitively, on every runtime. The member name in another casing, and .NET 8's `"0"`, are now a `JsonException`, and so are dictionary keys. A refusal names the JSON type that was sent ("A JSON object") and the names that would be accepted. Writing is unchanged. 0.48.0 said the member name was still read in any casing; that's no longer true. They now derive from the new `RivetStringEnumConverter<T>` (a `JsonConverterFactory`) instead of `JsonStringEnumConverter<T>`.
- CLI: `RIV4005` checks Azure Functions handlers. The worker reads a route value as JSON, so an enum with string wire values binds no name at all; use a plain enum or bind a `string`.

#### Fixes

- CLI: `--check` follows a `Match` arm held in a local or written as a local function, and a terminal handed to a helper, as in `return Done(endpoint.Success(x))`, no longer leaves the binding an `OrphanedBinding`.
- CLI: `RIV4005` and `RIV1110` stop missing enums ASP.NET binds piece by piece: an `[ApiController]` complex type with a `[FromQuery]` or `IFormFile` member, every complex parameter once `SuppressInferBindingSourcesForParameters` is set, MVC types nested at any depth, and minimal-API `[FromForm]` types (whose mapper ignores case).
- CLI: `--check` no longer overflows the stack on a local function that passes itself to the call it returns (`IResult Attempt() => Retry(Attempt);`).
- CLI: `RIV4005` and `RIV4006` bind the way the host does in three more places: minimal APIs read `StringValues` from the query on a body-less verb, a type with only a `[TypeConverter]` is a simple value on MVC but not on minimal APIs, and on MVC `Name =` on a complex `[From*]` parameter prefixes its members (`?f.Search=`, and `?f.q=` for a renamed member), while header members are never prefixed.

### Part 3: inputs, security and the corpora

#### Breaking

- `Rivet.Attributes`: security reads the way OpenAPI means it. `.Secure(scheme, scopes...)` adds one way in, so calling it twice gives two alternatives. `.AndSecure(...)` adds a scheme the same caller also needs, and `.OrAnonymous()` makes credentials optional. `.Secure("admin")` reads exactly as before. The numbered `.SecurityRequirement(order, ...)` calls are gone; re-import, or rewrite them as `.Secure`/`.AndSecure`. Security stays spec-only: nothing checks it at runtime.
- CLI: contract JSON (`--from`) keeps an endpoint's security in one place: `security` is now the full `{ "alternatives": [{ "schemes": [{ "name", "scopes" }] }] }` list. The old `{ isAnonymous, scheme }` shape and the separate `securityRequirements` property are gone, so rivet-ts has to write the new shape. One scheme listed twice in an alternative is refused as invalid contract JSON.
- CLI: `--from` reads contract JSON strictly. An unknown or retired property (`isAnonymous`, `securityRequirements`, a top-level key no producer writes) is refused as invalid contract JSON naming its path, and every member `rivet-contract-schema.json` marks required is enforced. Before, a stale producer's fields were silently dropped, so an endpoint could lose its security without a word. A required member, list entry or map value written as `null`, a contract with no `endpoints`, a type declaration carrying both `type` and `properties` (or neither), a response with no status, or a `statusKey` that isn't `default`, a range (`4XX` or `4xx`) or a three-digit code is refused the same way, and so is an example carrying both `json` and `componentExampleId`, which used to crash. rivet-ts and rivet-php write the new shape from their next releases.
- CLI: `--from-openapi` keeps every literal enum. An enum that couldn't become a C# enum (one value, booleans, numbers, mixed or out-of-range values, `[null]`) used to lose its values with `RIV3012`, and an untyped one became `string`. Now its C# type follows its values (`{ enum: [true] }` is a `bool`, `{ enum: [[]] }` a `JsonElement`) and the values travel in the generated metadata's new `enumJson` argument, so the spec re-emits them. Cloudflare's 207 `RIV3012`s are gone. An integer enum listing a value its C# type can't hold (`[-1, 18446744073709551615]` stays a `long`) keeps the values too, and the new `RIV3031` names the value C# can't hold. `RIV3012` is retired, and re-imported code changes type where an untyped enum used to be `string`.
- CLI: in contract JSON an endpoint parameter's deprecation flag is `deprecated`, as `rivet-contract-schema.json` always said, not `isDeprecated`. `--from` JSON using the schema's name used to be ignored. The schema itself now accepts every field Rivet writes (`minProperties`/`maxProperties`, scalar `format`/`required`/`enum`, the provenance references, param source `cookie`, `schemaDescription` and more), so rivet-ts and rivet-php need its new copy.
- CLI: contradictory security calls (`.Anonymous()` alongside `.Secure()`, or `.AndSecure()` with nothing to join) fail with the new `RIV1114`. Before, one call quietly won.
- CLI: `RIV4006` is an error, so an app whose handlers bind inputs differently from the contract now fails `--check`.
- CLI: a header parameter named `Accept`, `Content-Type` or `Authorization` stops generation with `RIV2009`, now an error, as the attributes reference always said. It used to be dropped from the spec with a warning, so clients never sent what the handler read. Describe media types with `.ProducesContentType(...)`/`.AcceptsContentType(...)` and credentials with a security scheme.
- CLI: a `SuppressInferBindingSourcesForParameters` assignment that isn't a compile-time constant stops `--check` and generation with the new `RIV1115` whenever an annotated MVC action (generation) or a contract's MVC implementation (`--check`) is on an `[ApiController]` controller, naming the file and line. Whether MVC infers binding sources decides what every parameter binds, so `RIV1110`, `RIV4005` and `RIV4006` used to answer on a guess.
- CLI: `--from-openapi` merges paths that differ only in parameter names (`/deployments/{id}` beside `/deployments/{idOrUrl}`, which OpenAPI forbids) into the first one, with the new `RIV3029`. The later operation's C# route and parameters take the first path's names. Nothing changes on the wire, because path parameter names are never sent. Paths that can't merge cleanly (a shared method, any path-level field on either path, a repeated parameter name, or an operation that `$ref`s a renamed path parameter) are left alone and stop generation with `RIV2013`.
- `Rivet.Attributes`: `RequestExampleJson`/`ResponseExampleJson` take a nullable `json` plus `summary:` and `description:`, and `RivetSchemaRef` takes an optional pointer and can repeat. Contract JSON's `endpointExample` gains `summary`/`description` and a form with no value. Re-import to regenerate.

#### Features

- CLI: `--check` compares each handler's bound inputs with its contract's and fails with `RIV4006` when they disagree: an input the handler binds that the contract never declares, one the contract declares that the handler never binds, or one bound from the wrong place. It reads binding the way ASP.NET does, inference and `Name =` included, so it catches an `[AsParameters]` member renamed with `[JsonPropertyName]` (the spec says `?q=`, ASP.NET reads `?Text=`) and an `[ApiController]` GET that takes its query record from the body. A `.FormEncoded()` body is compared field by field under its wire names, and a declared cookie is reported unless the handler reads the request. The form fields come from the same lowering as the spec, so `[RivetRequestBody]` on a `.FormEncoded()` endpoint is compared under its own fields. A handler that can read the request (an `HttpRequest` or `HttpContext` parameter, or a body that reads `Request`, `RouteData`, `ControllerContext.HttpContext.Request`, `IHttpContextAccessor.HttpContext.Request` or `HttpContext.GetRouteValue`, or hands the `HttpContext` or `HttpRequest` to another method) is trusted to read the rest by hand; touching only `HttpContext.User` or `Response` doesn't count. The `Authorization` header, a `.QueryAuth()` token and an apiKey scheme's header or query parameter belong to security, with schemes from attributes or `--security`, which `--check` now takes the same way generation does. Azure Functions handlers aren't compared.
- Corpora: stripe, slack, vercel, github and discord join the round-trip gate, which now proves 21 of the 25 committed specs survive import, compile and re-emit. The fixes that got them there are below.

#### Fixes

- CLI: `components.headers` survive import, and a header `$ref` stays a `$ref` on operation and component responses. They used to vanish, leaving component responses pointing at nothing.
- CLI: an Example Object keeps its `summary` and `description`, and one that is only a summary comes back as a whole example rather than a `missing-value` marker. A `$ref`'d example keeps its summary and description beside the `$ref`, and an example value shaped like `{"$ref": …}` stays data.
- CLI: an enum is a set. A repeated member collapses to one instead of giving the C# enum two members with one wire value (`RIV1106`).
- CLI: a `null` enum member survives import, separately from nullability. Both rules hold under a property or response named `default` or `example`, which used to be mistaken for example values.
- CLI: array items and map values in a typed record keep their `$ref` to a named scalar, and a nullable use of a component, enum or brand that already admits null is referenced bare, through aliases too (an alias of `unknown`, of a nullable enum or brand, a generic alias whose body admits null, a doubly nullable reference). The old `oneOf: [$ref, null]` matched null twice, so `oneOf` rejected null outright.
- CLI: `minProperties`/`maxProperties` survive on typed dictionaries instead of vanishing.
- CLI: OpenAPI 3.1's titled-const `oneOf` (`{ title, const }` per member) imports as an enum named by its titles. It used to be a union of identical slots nobody could tell apart, with a `RIV3015` each.
- CLI: a named boolean or number enum keeps its members, and the properties using it keep their `$ref`.
- CLI: a branded scalar keeps `readOnly`, `example` and its other annotations.
- CLI: a discriminator mapping into another file is dropped with `RIV3005`. Re-emitted, it used to crash the next import. A mapping value counts as a schema name only when a schema component has that name, as OpenAPI 3.1.1 says.
- CLI: emission and import read OpenAPI structure by one set of rules. An extension is a case-sensitive `x-` field, as the spec's "all field names are case sensitive" says. A property, response, component or callback named like a keyword (`default`, `examples`, `x-trace`) is structure, so `x-desc` and the other mapped and preserved extensions reach a property named `default`, and a property named `examples` is no longer read as a map of examples.
- CLI: a reference to a response, example or other non-schema component keeps its `description` beside it instead of being rewritten into a schema `allOf`, which stopped it being a reference.
- CLI: a non-string `x-desc`, parameter `name`/`in` or `swagger` field no longer crashes the import, and a non-string request-body `description` is refused as an invalid spec.
- CLI: a `$ref`'d path item's summary, description, `externalDocs` and callbacks are preserved, or reported, under the referencing path.
- CLI: `--from-openapi` never widens security. A requirement naming a scheme `components.securitySchemes` never defines used to pass through and fail the next emit with `RIV2002` (Cloudflare's `assets_jwt`). Now that alternative is dropped with the new `RIV3030`, since nobody could satisfy it anyway, and an operation left with none is dropped too, instead of being imported as open. The same holds for a document's global security, whose inheriting operations are dropped when none of it survives, unless import `--security` names a scheme for operations that declare none. The drop happens before anything else reads the document, so nothing the operation carried is left behind.
- CLI: an imported discriminator variant pinned to a component the import also kept verbatim `$ref`s that copy, instead of failing `RIV2001` against a shape rebuilt from C# without the descriptions.

- Diagnostics: the error list and every changed row are updated; `RIV2003`'s registry text no longer claims "the later definition wins". `RIV1009` joins the retired IDs, and so does `RIV3002`, which nothing had emitted since 0.41.0: the importer has kept every security alternative and its scopes since then.

## 0.48.0 — 2026-10-21

### Features

- `Rivet.Attributes`: `File(Func<Stream, Task> writer, ...)` serves a file the handler writes as it goes, such as a live transcode piping into the response. Every `File(...)` rule still applies before the writer runs: a declared binary success, a content type the contract covers, a concrete type for a media range, and a well-formed entity tag. `nosniff` and the inline disposition are sent as for any file. There is no `enableRangeProcessing`, because a body written as it goes has no byte ranges. Works with `.ToResult()` and `.ToActionResult()`, and `--check` counts it like any other `File(...)`.

### Fixes

- CLI: `--check` accepts a contract field's `.Route` as a minimal-API route, as in `app.MapGet(MembersContract.Health.Route, ...)`, which the Contracts guide has always recommended. Before, any route that wasn't a compile-time constant was reported as `RouteMismatch`, so you had to keep a `const string` next to every contract route. `MapGroup` prefixes still count, so a grouped route that doesn't match the contract is still reported.
- CLI: `--check` follows two common ways of returning a terminal that it used to miss, and reported as `MissingImplementation` and `OrphanedBinding`. The first is lambda arms, as in `return outcome.Match(ok => endpoint.Success(ok).ToActionResult(), ...)`, sync or async, in an action or a minimal-API handler. The second is one adapter around a whole switch or `?:`, directly or through a local holding it, as in `return (result switch { ... }).ToActionResult()`. A lambda counts only when it's passed straight to the call the handler returns, such as a `Match` arm; one buried in an argument, as in `Ok(items.Select(...))`, doesn't. A terminal that reaches the adapter through a helper still never counts.
- CLI: `--check` no longer counts a static method on a controller as an MVC implementation. MVC never routes a static method, so it was crediting coverage to an action that never runs; the field now shows as `MissingImplementation`, and a `Bind` in it as `OrphanedBinding`.
- CLI: a bound endpoint the handler hands to a helper whose answer it returns, as in `return Done(endpoint.Refuse(reason))` or a `Match` arm doing the same, is no longer an `OrphanedBinding`. The docs have always said a helper may take the bound endpoint. `--check` looks for it through the same `await`, casts, `switch`, `?:` and locals it follows for terminals, and counts a C# 14 extension block's receiver as well as a classic extension's. Coverage is unchanged: a field still needs a terminal the handler returns itself.
- `Rivet.Attributes`: a stream file the adapter refuses, because the host already started the response or set another status, is now disposed. Before, nothing disposed it.
- Docs: `RIV3004` and `RIV3013`, retired in 0.42.0 but still registered with a "Retired" row, are gone from the registry and get tombstones like every other retired ID. `RIV3007` gets the tombstone it was missing, and the tombstones move to their own section at the end of the diagnostics page instead of sitting under extraction.
- Tests: each target framework's tests run on that framework's runtime. A repo-wide `RollForward=LatestMajor` had been running the net8.0 and net9.0 runs on .NET 10, which hid that .NET 8 still reads `"0"` for a strict enum. Only the CLI rolls forward now, so it still runs on whatever newer .NET a consumer has.

### Breaking

- `Rivet.Attributes`: on MVC, contract files (bytes, streams and physical paths) now go through the same ASP.NET file results that minimal APIs and writers already used, rather than MVC's `FileContentResult`, `FileStreamResult` and `PhysicalFileResult`. Ranges, conditional requests, disposition and headers come out the same on both hosts, and the tests pin each one on both. The catch: if your app replaced MVC's file-result executors, Rivet files no longer go through them.
- `Rivet.Attributes`: `RivetLowerCaseEnumConverter`, `RivetCamelCaseEnumConverter`, `RivetSnakeCaseEnumConverter` and `RivetKebabCaseEnumConverter` refuse integers. A JSON `0` for one of these enums is now a `JsonException` on every runtime instead of being read as the member with that value, and so is a numeric string `"0"` from .NET 9 on (.NET 8's System.Text.Json still reads it). The C# member name is still read in any casing, as System.Text.Json always has. An enum with no converter is still an integer, and System.Text.Json's own `JsonStringEnumConverter` is unchanged. Route, query, header and form parameters are bound by ASP.NET, not by these converters, so this doesn't change them. An app that registered a global strict `JsonStringEnumConverter` to get this behaviour can drop it only if every enum it serializes carries a Rivet converter: a global converter also turns enums with no converter into strings, and dropping it makes those integers on the wire.
- CLI: an enum parameter bound from the route, query, header or form now has to be bindable with every wire value the spec lists. The spec has always advertised the converter's names for it, but ASP.NET binds these values itself: minimal APIs need each name to equal the member name exactly, MVC needs it to equal ignoring case. So a camelCase or lowercase converter advertised values a minimal API answers with 400, and snake, kebab or a rename that changes more than the casing did the same on both hosts. `--check` now refuses that with `RIV4005` for a handler implementing a contract (Azure Functions handlers aren't checked), and generation refuses it with `RIV1110` for an annotated action (`[RivetEndpoint]` or `[RivetClient]`; a static `[RivetEndpoint]` handler gets the minimal-API rule). Use a plain enum, the built-in `JsonStringEnumConverter<T>` with no renames, or bind a `string` and parse it yourself. A contract on its own isn't checked at generation, because generation can't see how the handler binds.

### Docs

- Contract Coverage: a "Helpers are fine" section. The spec comes from the contract, so an `.Error(...)` or a 404 guard can live in a shared helper, and `--check` only needs each handler to return one terminal on its contract.
- Limitations: an "Enum parameters are bound by ASP.NET" section, with what each host accepts for an enum in the route, query, header or form, what Rivet checks, and the three ways to fix a failing check. The converter docs no longer claim a JSON body accepts exactly the spec's names: integers are refused, and the member name still gets through in any casing.

## 0.45.0 — 2026-09-29 (breaking)

- `Rivet.Attributes`: removed the unused `RouteDefinitionBase.IsFileUpload` getter.
- Import: an operation with `security: []` now scaffolds `.Anonymous()` instead of `.SecurityRequirements()`. Both re-emit `security: []`.
- `Rivet.Attributes`: removed the protected `RouteDefinitionBase.BeginMutation()` and `CopyStateTo()` helpers. Builder state is now one immutable record behind a private gate.
- `Rivet.Attributes`: removed the 18 five-parameter `File(content, downloadName, enableRangeProcessing, lastModified, entityTag)` overloads on `RouteDefinition`, `RouteDefinition<T>`, `FileRouteDefinition` and the three `Bound*` types. Source calls still bind to the six-parameter overload (`contentType` defaults to `null`); assemblies compiled against the old overloads must be rebuilt.
- `Rivet.Attributes`: removed the test-only getters on `RouteDefinitionBase` (`EndpointSummary`, `EndpointDescription`, `IsAnonymous`, `SecurityScheme`, `FileContentType`, `IsFormEncoded`, `BinaryRequestContentType`, `RequestContentType`, `ResponseContentType`, `IsQueryAuth`, `QueryAuthParameterName`, `RouteErrorResponses`, `ResponseHeaders`, `SuccessStatusCode`, and the protected `SuccessStatus`) and the `RouteResponseHeader` record. Spec-only builder methods (`Summary`, `Description`, `Anonymous`, `Secure`, `QueryAuth`, `WithResponseHeader*`, the example, security-requirement, request-content and `Parameter<T>` markers) no longer record anything at runtime; Rivet.Tool reads them from syntax. They still throw after publication.
- `Rivet.Attributes`: declaring the same response header twice for one status no longer throws at runtime.
- `Rivet.Attributes`: `RouteErrorResponse` and `RivetUnionJsonConverter<T>` are now internal (`[RivetUnion]` still constructs the converter).
- `Rivet.Attributes`: a subtype payload where a concrete type is declared is now rejected when the result executes, not when `Success(...)`/`Error(...)` is called. The check uses the host's serializer options, so polymorphism configured through a `TypeInfoResolver` is honoured, not only `[JsonPolymorphic]`/`[JsonDerivedType]` attributes.
- `Rivet.Attributes`: declared response media types match on the type without parameters, so `text/csv; charset=utf-8` and `text/csv` are one representation. A body response whose selected content type is malformed is now a contract violation.
- Import: every disambiguated name now uses one `Name_2`, `Name_3`… scheme. Synthetic types that used to be `Foo2` are now `Foo_2` (for example, slack's `InfoResponseDefaultContent12` is now `InfoResponseDefaultContent1_2`). Enum members and contract fields also skip a suffix that the spec already authored.
- Import: inline schemas that differ in `oneOf`/`anyOf`/`allOf`/`const`/`not` now get distinct synthetic types instead of silently sharing the first one.
- Import: a Swagger 2 `basic` security definition now imports as HTTP `basic`; before, it was refused.
- Import: a malformed spec (invalid JSON, missing required fields) now exits 1 with `error: invalid OpenAPI document: …` instead of a stack trace.
- Analysis: attributes are matched by symbol, not by simple name. A same-named attribute from another namespace (for example a custom `RequiredAttribute`) no longer counts as the Rivet, DataAnnotations or System.Text.Json attribute.
- Analysis: nested types are now discovered, so a `[RivetContract]`, `[RivetType]`, `[RivetClient]` or `[RivetEndpoint]` class nested in another class is no longer silently skipped.
- Analysis: a C# `required` field (a `[JsonInclude]` field) is now required in the schema, as a `required` property already was.
- Analysis: a contract field's builder chain is read through Roslyn operations. A chain that does not start at a `Define` member is no longer read, and a call in the chain that is not a Rivet builder method (such as a user extension named `Returns`) is refused instead of being interpreted by name.
- `--from` contract JSON: the reader now enforces the members `rivet-contract-schema.json` requires on type nodes (`kind`, a primitive's `type`, `inner`, `element`, `values`, and so on) and the `type` of every param, response header and property. A missing one now fails with exit 1 and a JSON error. Before, it was either silently emitted as an untyped `{type: object}` or crashed with a stack trace. Schema-valid contracts, including rivet-ts output, are unaffected.
- OpenAPI emission: a `[RivetDefault]`/`[RivetExample]` value, or a schema-metadata default/example, that is not a JSON literal is now refused with exit 1. Before, property values fell back to a raw string and the other paths crashed with a stack trace.
- Diagnostics: retired `RIV3007` (alias `$ref` cycle). Nothing emitted it; alias cycles are reported as `RIV3001`. The ID is not reused.
- `Rivet.Attributes`: `[RivetConstraints]` keeps only `MultipleOf` and `UniqueItems`. `ExclusiveMinimum`/`ExclusiveMaximum` are gone; use `[Range(…, MinimumIsExclusive = true, MaximumIsExclusive = true)]`. `MinItems`/`MaxItems` are gone; use `[MinLength]`/`[MaxLength]`/`[Length]` on the collection. Rivet reads `[MinLength]`/`[MaxLength]`/`[Length]` as `minItems`/`maxItems` on an array property (before, `[MaxLength]` on a list emitted a string `maxLength`) and reads `[Length]` at all. Import scaffolds the DataAnnotations form. A schema that declares both the inclusive and the exclusive bound of one side imports the tighter one.
- CLI: `--project` is only ever a project file. `--project Contracts.cs` used to fall back to compiling the positional `.cs` files; it now tries to load `Contracts.cs` as a project and fails. Pass `.cs` files positionally. A positional `.csproj` is the project wherever it appears in the argument list, not only first.
- `Rivet.Attributes`: removed the implicit conversions from every route-definition type to `Define` (they returned `default!`). Declare contract fields with the builder's own type, for example `public static readonly RouteDefinition<TaskDto> Get = Define.Get<TaskDto>("/tasks/{id}");`. Rivet no longer discovers `Define`-typed fields.
- `Rivet.Attributes`: removed the 22-argument `RivetGeneratedSchemaMetadataAttribute` constructor. Rivet no longer reads the short form; re-import to regenerate code that used it.
- `Rivet.Attributes`: `Error` and `File` terminals are declared once, on the new abstract `TerminalRouteDefinitionBase<TSelf>` (base of `RouteDefinition`, `RouteDefinition<T>` and `FileRouteDefinition`) and `BoundRouteDefinitionBase` (base of the three `Bound*` types). Source calls are unchanged; assemblies compiled against the old declaring types must be rebuilt.
- `Rivet.Attributes`: removed the `FileRouteDefinition.ContentType(…)` and `FileRouteDefinition<TInput>.ContentType(…)` aliases. Use `.ProducesFile(…)`. Import now scaffolds `.ProducesFile("…")` on `Define.File(...)` endpoints.
- Analysis: a contract endpoint that declares the same response header twice for one status (case-insensitively, e.g. `ETag` and `etag`) now fails with `RIV1109`. Before, both spellings were emitted.
- `Rivet.Attributes`: removed the no-argument `.SecurityRequirements()` builder method; it declared the same `security: []` as `.Anonymous()`. Use `.Anonymous()`.
- OpenAPI emission: an inline object whose derived component name is taken and no descriptive name fits is now named `Name_2`, `Name_3`… (was `Name2`), the same scheme import uses.
- Import: a response header declared on both a range status (`4XX`) and `default` now imports for both. Before, the second was dropped because both statuses shared the numeric key 0.
- Analysis: nullability no longer makes an object-schema property optional. System.Text.Json writes `null`, so a `T?` property is now `required` with a `T | null` type; it was omitted from `required` (clients saw `x?: T | null`). A property is optional only with `[RivetOptional]` or `[JsonIgnore(Condition = WhenWritingNull/WhenWritingDefault)]`. This includes multipart input records, whose nullable parts now need `[RivetOptional]` to stay optional. Query, header and form parameters keep binder semantics (nullable ⇒ optional). `[Required]` and the C# `required` keyword no longer affect requiredness anywhere: object properties are required by default, and the emitter already treated every nullable parameter as optional. **Migration:** add `[RivetOptional]` to each nullable property clients may omit. Import already scaffolds `[RivetOptional]` for every property a spec leaves out of `required`, so imported code round-trips unchanged.
- `--from` contract JSON: an inline-object property without an `optional` flag is now required even when its type is nullable (the nullable ⇒ optional fallback for older IR is gone). rivet-ts always writes the flag for nullable properties, so its output is unaffected.
